0. VUE D'ENSEMBLE
================================================================================

CyberWatch AI est une plateforme web qui collecte AUTOMATIQUEMENT les
vulnérabilités de cybersécurité (CVE = Common Vulnerabilities and Exposures)
depuis des sources fiables (NVD, Microsoft MSRC, CISA...), les vérifie via un
agent intelligent, puis les met à disposition d'un consultant pour consultation
et analyse.

Le système repose sur DEUX rôles distincts :

  +-------------------+---------------------------------------------------------+
  | RÔLE              | RESPONSABILITÉ                                          |
  +-------------------+---------------------------------------------------------+
  | ADMIN             | Gère les SOURCES : ajouter, vérifier (agent), valider,  |
  |                   | activer/désactiver, supprimer, configurer les secrets.  |
  +-------------------+---------------------------------------------------------+
  | CONSULTANT        | CONSULTE les CVE collectées (recherche, filtres,        |
  |                   | détail) et configure la PLANIFICATION de la collecte.   |
  +-------------------+---------------------------------------------------------+

Idée forte du projet : un « agent de vérification » et un « agent de collecte »
INTELLIGENTS qui choisissent automatiquement la meilleure méthode de collecte
(API / RSS / Scraping) en VALIDANT réellement la présence de données CVE.

3.1  PAGE — CONNEXION (SignIn)
--------------------------------------------------------------------------------
Fichier    : app/frontend/src/pages/auth/SignIn.jsx
Routes     : /admin/signin  et  /consultant/signin
Rôle       : public
But        : permettre à un utilisateur de se connecter selon son rôle.

Contenu / champs :
  - E-mail
  - Mot de passe
  - Bouton « Se connecter »
  - Lien vers la page d'inscription du même rôle

Fonctionnement :
  - Envoie POST /auth/login { email, password, role }
  - Le backend vérifie le mot de passe (haché) et renvoie un JWT + le profil
  - Le token est stocké côté client et ajouté à chaque requête (Axios)
  - Redirection automatique vers l'espace du rôle.

--------------------------------------------------------------------------------
3.2  PAGE — INSCRIPTION (SignUp)
--------------------------------------------------------------------------------
Fichier    : app/frontend/src/pages/auth/SignUp.jsx
Routes     : /admin/signup  et  /consultant/signup
Rôle       : public
But        : créer un compte (Admin ou Consultant).

Contenu / champs :
  - Nom complet
  - E-mail
  - Mot de passe
  - Bouton « Créer le compte »

Fonctionnement :
  - Envoie POST /auth/signup { full_name, email, password, role }
  - Un compte est créé (rôle fixé par la page), un JWT est renvoyé.
  - E-mail déjà utilisé -> message d'erreur.

--------------------------------------------------------------------------------

Route      : /admin/sources/new

  - Description (optionnelle)

3.5  PAGE — DÉTAIL D'UNE SOURCE (SourceDetail)
--------------------------------------------------------------------------------
Fichier    : app/frontend/src/pages/admin/SourceDetail.jsx
Route      : /admin/sources/:id
Rôle       : admin
But        : consulter/modifier une source, relancer la vérification, gérer les
             secrets et déclencher la collecte. C'EST LA PAGE LA PLUS RICHE.

Contenu — carte « COLLECTE » (rapport de l'analyseur de méthode) :
    - Méthode détectée (API / RSS / Web Scraping)
    - Authentication (Aucune / requise / configurée)
    - API Endpoint (l'URL réelle de collecte, ex. l'API NVD/MSRC)
    - Data Format (JSON / XML / HTML)
    - Méthode de repli (fallback : API -> RSS -> Scraping)
    - Validation de la méthode : Réussie / Échec + nb de CVE + score /100
    - Décision / Explication (pourquoi cette méthode a été retenue)
    - Méthodes testées : liste de chaque candidat avec statut
        validé (v) / rejeté (x) / indisponible (-), nb de CVE et score
    - Bloc « Authentification » : saisie du secret (API Key / Bearer / Basic /
      OAuth) — stocké CHIFFRÉ, jamais réaffiché.

Contenu — carte « INFORMATIONS » :
    - Nom, URL, Description (modifiables)
    - Boutons : Tester la connexion | Activer/Désactiver la collecte |
      Relancer la collecte | Enregistrer

Contenu — carte « VÉRIFICATION » :
    - Le rapport AdminVerification (verdict, résumé, score, niveaux 1 & 2),
      idem à la page Nouvelle source.
    - Bouton « Relancer » (relance l'agent de vérification).
    - Bouton « Supprimer la source ».

Endpoints appelés :
  - GET    /admin/sources/{id}
  - PUT    /admin/sources/{id}                     (modifier / statut)
  - POST   /admin/sources/{id}/verify              (re-vérifier)
  - POST   /admin/sources/{id}/test-connection     (test de connexion)
  - POST   /admin/sources/{id}/trigger-collection  (collecter maintenant)
  - PUT    /admin/sources/{id}/credentials         (enregistrer le secret)
  - DELETE /admin/sources/{id}/credentials         (supprimer le secret)
  - DELETE /admin/sources/{id}                      (supprimer la source)

4. LES AGENTS (LE CŒUR DU BACKEND)
================================================================================

--------------------------------------------------------------------------------
4.1  AGENT DE VÉRIFICATION      (services/verification/agent.py)
--------------------------------------------------------------------------------
Lancé lors de l'ajout / re-vérification d'une source. Produit un rapport avec un
score global et une décision (FIABLE / À SURVEILLER / NON FIABLE).

Il compose plusieurs briques :

  (a) http_client.py       Requête HTTP réelle (statut, TLS, type de contenu,
                           corps de la page).

  (b) browser_client.py    Rendu de la page avec un navigateur Chromium
                           (Playwright) quand la page est dynamique (JavaScript)
                           ou bloquée par une protection anti-bot.

  (c) Collection Method Analyzer  (method_analyzer.py) — voir 4.2

  (d) technical.py         NIVEAU 1 — Vérification technique :
                           URL renseignée, URL accessible (HTTP 200),
                           HTTPS/TLS, contenu cohérent avec la méthode.

  (e) credibility.py       NIVEAU 2 — Vérification de crédibilité :
                           domaine d'organisation officielle, liste blanche,
                           présence de CVE, existence du CVE dans la base NVD...

  (f) cve.py               Extraction des identifiants CVE (regex CVE-AAAA-NNNN)
                           et validation d'existence via l'API officielle NVD.

  (g) cve_dates.py         « Publie aujourd'hui ? » — extrait la date de
                           publication de CHAQUE CVE (API / RSS / HTML) et la
                           compare à la date du jour (pas une simple présence de
                           la date dans la page).

  Score global = 40% technique + 60% crédibilité.
  Seuils : >= 70 FIABLE, 40..69 À SURVEILLER, < 40 NON FIABLE.

--------------------------------------------------------------------------------
4.2  COLLECTION METHOD ANALYZER  (services/verification/method_analyzer.py)
--------------------------------------------------------------------------------
Choisit la MEILLEURE méthode de collecte en la VALIDANT réellement (une méthode
n'est jamais retenue seulement parce que la technologie existe).

Ordre de priorité (chaîne de repli / fallback) :
    1. API officielle            (registre d'API connues + détection JSON/XML)
    2. Flux RSS/Atom             (validé UNIQUEMENT s'il contient des CVE)
    3. API interne JavaScript    (endpoints fetch/XHR repérés dans la page)
    4. Scraping dynamique        (rendu navigateur Playwright)
    5. Scraping HTML classique   (HTML brut)

Score de pertinence (CVE Detection Score) attribué à chaque méthode testée :
    + 50  au moins un identifiant CVE présent
    + 20  date de publication trouvée
    + 20  description de vulnérabilité trouvée
    + 10  score CVSS trouvé
  Seuil de validation : 50. En dessous, la méthode est jugée NON adaptée
  et on passe à la suivante.

Registre d'API officielles connues (exemples) :
    NVD    -> https://services.nvd.nist.gov/rest/json/cves/2.0
    MSRC   -> https://api.msrc.microsoft.com/sug/v2.0/en-US/vulnerability
    CISA   -> .../feeds/known_exploited_vulnerabilities.json
    + CIRCL, Red Hat, GitHub Advisories

Exemple concret (Microsoft MSRC) :
    - La page /update-guide/vulnerability est dynamique : HTML brut = 0 CVE.
    - Un « RSS » éventuel ne contient pas de CVE  -> RSS rejeté.
    - L'API officielle MSRC renvoie 126 CVE       -> Méthode = API, validée.
    - Résultat : Contains CVE = True.

--------------------------------------------------------------------------------
4.3  AGENT DE COLLECTE          (routers/admin.py : _collect_with_fallback)
--------------------------------------------------------------------------------
Déclenché par « Relancer la collecte » (ou par la planification).
Applique le repli en conditions réelles : essaie l'API, puis le RSS, puis le
scraping, et enregistre la méthode réellement utilisée (method_used) dans
l'historique de collecte. Une API protégée sans secret configuré est bloquée.

6. FLUX PRINCIPAL DE BOUT EN BOUT
================================================================================

  1) ADMIN se connecte -> /admin/sources
  2) ADMIN clique « Nouvelle source », saisit Nom + URL -> POST /admin/sources
     -> détection rapide de la méthode.
  3) L'agent de VÉRIFICATION se lance -> POST .../verify
        - fetch de la page (+ rendu navigateur si dynamique)
        - Collection Method Analyzer : teste API/RSS/JS/dynamique/HTML,
          valide par présence de CVE (score), choisit la meilleure méthode
        - Niveau 1 (technique) + Niveau 2 (crédibilité) -> score + verdict
  4) ADMIN valide la source (statut = validated).
  5) COLLECTE (bouton « Relancer » ou planification) -> agent de collecte
     avec repli API -> RSS -> Scraping -> insertion des CVE dans « cves ».
  6) CONSULTANT se connecte -> /consultant/cves : recherche, filtre, ouvre le
     détail d'une CVE ; configure la planification dans /consultant/schedule.
